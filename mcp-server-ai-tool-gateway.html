MCP Servers — The AI Tool Gateway Explained

Model Context Protocol sits between an LLM and everything it can do. One standardized interface. Four primitives. Five inspection layers. And a single security boundary that sees every tool call, data read, and prompt request the agent makes.

SV
Sam Vuillaume — Consulting Systems Expert, Cloud & AI Security · Fortinet
May 26, 2026 · ~6 min read · Field · PreSales · Architecture

One sentence

An MCP server is a structured bridge that exposes tools, data, and prompts to an LLM through a uniform JSON-RPC interface — while controlling and observing every interaction that crosses it.

Think of MCP as the API gateway for AI agents. Nothing reaches a tool, dataset, or prompt template without passing through it first.

The four primitives

MCP standardizes exactly four interaction types. Together they cover everything an agent needs: discovering capabilities, executing actions, reading data, and fetching prompts.

🧰 tools/list Discovery

"What can I call?" — the model asks, the server returns tool names, input schemas, and permissions. The model never needs to know how tools are implemented.

⚙️ tools/call Execution

"Run this." — the model sends a tool name and arguments. The server validates, enforces policy, executes, logs, and returns the result — or denies.

📂 resources/read Data access

"Give me this data." — the model requests a URI (file, database record, API-backed resource). The server resolves it, enforces ACLs, and returns content within policy bounds.

💬 prompts/get Prompt templates

"Give me the incident triage template." — centrally managed, versioned prompts served on demand. Variables resolved server-side before delivery. Prompt injection surface is visible here.

json-rpc · tools/call example
→ Request
{ "method": "tools/call", "params": { "name": "get_user_data", "arguments": { "id": 123 } } }

← MCP server: validate → enforce policy → log → execute → return result

Five layers of inspection

Every MCP exchange passes through a single protocol handler. That handler applies five layers before any action reaches the outside world:

A

Request interception — the server sees every message: tool name, arguments, caller identity, context metadata. It can validate, block, modify, or log before forwarding.

B

Schema validation — required fields, types, and value constraints are checked before execution. If a tool expects user_id: integer, "DROP TABLE users" is rejected here.

C

Policy enforcement — RBAC, tenant isolation, data residency rules, and per-tool allow/deny lists enforced here. Even if the model requests a call, the server can respond: ❌ Denied — tool not allowed in this tenant.

D

Audit logging — every tools/list, tools/call, resources/read, and prompts/get is logged with full inputs. The complete agent session is reconstructable from MCP logs alone — SOC 2, ISO 27001, and NIST 800-53 alignment follows naturally.

E

Response shaping — sensitive fields redacted, large payloads truncated, formats normalized before the model sees the result. The agent gets only what policy allows — even if the source returned more.

What this enables

  • Zero-trust tool execution — every call validated and authorized, not assumed safe
  • Prompt injection containment — malicious content in prompts/get filtered before the model sees it
  • Data exfiltration control — resources/read responses inspected and shaped before return
  • Full auditability — NIST 800-53 AC, AU, SC control families achievable through MCP logging alone

The corresponding risk

MCP server is a high-value security boundary. Compromise gives an attacker full visibility into every tool the agent can call, every argument it passes, and every resource it reads — across all tenants. Treat it with the same posture as a production API gateway or cloud IAM service.

Mental model — Kubernetes API Server for AI

The most durable analogy: MCP server is to AI agents what the Kubernetes API server is to workloads. Every capability request flows through it. Nothing bypasses it.

Fortinet reference architecture — protecting MCP at scale

How you protect MCP servers depends on where they run. Two deployment patterns, two Fortinet answers.

🔷 Pattern 1 — MCP servers hosted in Kubernetes (CSP)

The naive deployment: each MCP server exposed as a Kubernetes Service type: LoadBalancer. Every service provisions its own cloud load balancer — its own public IP, its own cost, its own attack surface. Ten MCP servers = ten external LBs, ten ingress points to monitor, ten certificates to manage.

The FortiWeb answer: one Ingress Controller, one enforcement point for all.

FortiWeb — API Gateway + Kubernetes Ingress Controller

FortiWeb's Kubernetes Ingress Controller converts K8s Ingress resources into FortiWeb virtual servers and content-routing rules on a single backing appliance (VM or physical). All inbound MCP traffic — regardless of which MCP server it targets — flows through one external endpoint, where FortiWeb applies:

  • WAF — OWASP Top 10, injection, XSS, protocol anomaly detection across every MCP route
  • API schema validation — OpenAPI / JSON schema enforcement; malformed tools/call arguments rejected before reaching the MCP server
  • Bot protection + rate limiting — prevents automated enumeration of tools/list and brute-force prompt retrieval
  • mTLS + API key management — authentication enforced at the gateway before MCP protocol is even parsed
  • Single audit trail — all MCP traffic logged at one point, not scattered across per-service logs

Key differentiator: instead of N cloud load balancers for N MCP servers, you get one FortiWeb protecting all your MCPs — with consistent policy, unified logging, and a single security perimeter across the entire agent tool layer.

🔶 Pattern 2 — SaaS-backed or cloud-hosted MCP endpoints

When the MCP server is delivered as a managed SaaS service — or hosted on cloud infrastructure without a self-managed K8s cluster — there is no Ingress Controller to deploy. The protection layer moves to the cloud edge.

FortiAppSec Cloud — API security for SaaS-delivered MCPs

FortiAppSec Cloud is Fortinet's cloud-native SaaS platform for web application and API security — no appliance, no infrastructure to manage. For MCP endpoints exposed as cloud APIs it delivers:

  • API Gateway — API key management, access control, rate limiting per consumer or tenant
  • API schema enforcement — OpenAPI / JSON validation; rejects structurally invalid MCP requests before they reach the server
  • WAF + DDoS mitigation — hosted across AWS, Azure, and GCP regions, closest to where your MCP traffic originates
  • Bot and abuse protection — prevents automated scanning of tools/list or mass prompts/get harvesting
