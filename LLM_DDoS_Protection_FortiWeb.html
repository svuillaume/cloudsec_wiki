Overview

Large language model services are uniquely fragile under coordinated load because every request is computationally expensive. A traditional web API call costs microseconds; an LLM inferenceLLM inference — the process of running a trained model to produce output for a given prompt. Each inference consumes GPU compute and memory proportional to the input and output token count, which is why one expensive request can cost thousands of times more than a normal web request. request can take hundreds of milliseconds and consume significant GPU memoryGPU memory (VRAM) — the high-speed memory on a graphics processor where the model weights and the in-flight request context (the KV cache) live. Long-context prompts hold more of this memory for longer, so a flood of large prompts can exhaust VRAM and stall every concurrent request.. That asymmetry — cheap to request, expensive to serve — is exactly what a DDoSDDoS (Distributed Denial of Service) — an attack that overwhelms a service with traffic from many sources until legitimate users can no longer be served. Against LLMs the goal is often not raw bandwidth but resource exhaustion: burning GPU time and memory, and the cloud budget that pays for them. actor exploits.

What are LLM DDoS attacks?

Unlike a classic volumetric flood, an LLM DDoS targets the per-request cost rather than the network pipe. A few hundred carefully shaped requests per second can degrade or topple a model endpoint that happily serves thousands of cheap requests. The attacker's economics are favorable: each malicious request is trivial to send and very expensive to serve.[1][3]

Attack Vectors

  • Token floodingToken flooding — sending requests packed with very long contexts (for example 8K tokens each) at high frequency. Because GPU memory and compute scale with token count, a stream of maximal-length prompts exhausts VRAM far faster than the same number of short requests.: thousands of long-context prompts per second to exhaust GPU memory.
  • Expensive computation loops: prompts that force costly model operations — e.g. forcing chain-of-thought reasoning on every request.
  • Concurrent session attacks: bots open many connections and never close them, exhausting connection pools.
  • Prompt injectionPrompt injection — crafting input that manipulates the model into ignoring its instructions or producing attacker-chosen behavior. Combined with volume, an injected prompt can be tuned to maximize output length and therefore cost on every single request. + volume: prompts designed to generate maximally expensive responses, combined with request flooding.

The economics of the attack

A chatbot using a frontier model costs roughly $0.03 per 1K tokens. A 10-minute flood pushing 1M malicious tokens burns about $300 in compute alone — before counting downtime, SLA penalties, and lost customer trust. The attacker spends almost nothing to inflict it.[3]

Typical impacts include:

  • Service slowdowns and increased latency (response-time degradation).
  • API failures and complete outages during peak attacks.
  • Thousands of dollars in wasted cloud compute (GPU hours consumed by junk traffic).
  • Compliance violations (SLA breaches, regulatory uptime mandates).
  • Reputational damage and lost customer confidence.

FortiWeb Strategies

FortiWeb defends an LLM application DDoS in layers. The strongest place to start is prevention — stopping the automated traffic that powers a flood before it ever reaches a rate counter or the model.

Preventative measure

1

Bot & ML-based bot detection

An LLM application DDoS is, at scale, an automated attack — a fleet of clients hammering the API. So the highest-leverage preventative control is to separate bot from human at the door and drop the bots before any rate budget is spent. FortiWeb does this with three complementary engines:

  • Known-bot signatures & FortiGuard feeds — block recognized bad bots, scrapers, and tools by signature and reputation.
  • ML-based bot detectionML-Based Bot Detection — a FortiWeb engine that builds a behavioral model of how real clients interact with the application (request cadence, sequence, headers, fingerprint) and scores each client human-vs-bot in real time — catching novel automation that no static signature covers, with no CAPTCHA shown to real users. — a behavioral model scores each client human-vs-bot in real time, catching automation that mimics legitimate traffic and has no known signature.
  • Threshold & crawler heuristics — rapid-request and crawl-pattern detection flags clients behaving like a flood source.
fortiweb · bot mitigation (illustrative) 
# Web Protection > Bot Mitigation
set known-bots enable            # signature + FortiGuard bot reputation
set ml-based-detection enable    # behavioral model: human vs bot
set threshold-detection enable   # rapid-request / crawler heuristics
set action block                 # ML-flagged bots dropped — no CAPTCHA

✔ Removes the automated volume that powers a flood before rate counters even engage, and stays user-transparent (no CAPTCHA).   ✘ A determined attacker can rotate fingerprints — pair it with the ML anomaly engine below so rotated bots still surface as a traffic-shape anomaly.

Cost-limiting strategies

Beyond prevention, these patterns address the other token — the LLM text token that drives GPU cost (not the auth token). Until native LLM-token metering ships, three practical patterns approximate per-prompt cost limiting on FortiWeb today — listed from roughest to most accurate. They are not mutually exclusive; the strongest posture combines all three. (CLI below is illustrative — the actual FortiWeb stanzas live under HTTP Protocol Constraints / API Protection and Custom Rules, not a single rate-limit block.)

1

Payload size as a proxy (rough)

Cap the request body size — payload bytes correlate loosely with token count. In FortiWeb this is an HTTP protocol constraint / API-protection body-size limit, not a rate-limit knob:

fortiweb · body-size constraint (illustrative) 
# Web Protection > Protocol Constraints (or API Protection body limit)
set max-body-length 32768       # ~32 KB ≈ ~8K tokens (GPT-3 tokenizer)
set action block
# Adjust the byte-to-token multiplier to match your model's tokenizer

✔ Simple, no external dependency.   ✘ Inaccurate — compression, padding, and encoding differences skew the byte↔token ratio.

2

Header-based enforcement via the app's token decision (accurate)

FortiWeb can match a custom HTTP header in a Custom Rule and block on it — but it can't sum a numeric X-Token-Count into a per-minute budget; that aggregation isn't a FortiWeb primitive. So the app or API gateway owns the token math and keeps the running total, then sets a flag header once a user exceeds budget. FortiWeb consumes the decision, not the count:

fortiweb · custom rule (illustrative) 
# App/gateway counts tokens, sets a flag when the user is over budget:
#   X-Token-Budget-Exceeded: true

# FortiWeb Custom Rule — match the flag header, block:
match:  HTTP header  X-Token-Budget-Exceeded  ==  "true"
action: deny (or redirect / challenge)

✔ Accurate — trusts the application's own token accounting.   ✘ Requires app-side instrumentation to count tokens and set the flag; FortiWeb enforces the verdict, it doesn't meter tokens itself.

3

Endpoint-level rate limits (practical)

Different LLM operations have predictable cost profiles — limit each endpoint to match its weight, no token awareness needed:

fortiweb · per-endpoint limits 
/api/embeddings     -> 10 req/sec    # small payloads, fast
/api/completions    ->  2 req/sec    # large payloads, slow
/api/fine-tune      ->  1 req/hour   # resource-heavy

✔ Practical, no token awareness needed.   ✘ Doesn't account for prompt-size variance within an endpoint.

Combine, don't choose

Endpoint limits (3) set sane per-operation ceilings, payload-size limits (1) catch oversized prompts cheaply, and a trusted X-Token-Budget-Exceeded flag (2) adds true token accuracy where you control the app. Layer all three under ML-based anomaly detectionML-Based Anomaly Detection — FortiWeb's behavioral baseline engine. It backs up every static workaround on this page by catching deviations the fixed thresholds miss. and the static thresholds stop being your only line of defense.

Per-auth-token rate limiting & credential-abuse defense

Continuing the strategies above: the cost-limiting patterns addressed the LLM text token; this section addresses the auth tokenAuth token — the API credential in the Authorization: Bearer <token> header (e.g. sk-ant-…), or the API key in x-api-key. FortiWeb can match and rate-limit on it; it is not the LLM text token the model bills compute for. So "token-aware rate limiting" means rate-limiting per credential — a real FortiWeb capability. — the credential carried in each request.

The single most useful thing FortiWeb can do in front of an external LLM API (Anthropic, OpenAI, Gemini, or your own) is to treat the auth token / API key as the rate-limit key. Instead of throttling by source IP — which collapses every user behind a NAT or a shared egress into one bucket — FortiWeb scopes the limit to each unique credential. That single design choice gives you per-key quotas, instant revocation, and blast-radius isolation when a key leaks.

Be precise about the boundary, though: FortiWeb rate-limits and blocks by the auth token's value, pattern, and behavior — it does not validate whether that token is legitimate. The authentication decision stays with the application or model provider. FortiWeb is the cheap, fast filter that strips malformed, brute-forced, and revoked credentials before they ever reach the backend.

1

Rate-limit per auth token

Extract the auth token from Authorization: Bearer <token> and scope the quota to each unique value — so one noisy or compromised key can't starve everyone else:

fortiweb · per-token rate limit (illustrative) 
config waf http-request-rate-limit
    edit llm-per-token-quota
        set action block
        set uri-match-type prefix
        set uri "/v1/"                     # OpenAI / Anthropic API paths
        set limit-to-request 1000          # per token, per period
        set request-period 3600            # 1 hour
        # Scope the limit to the credential, not the source IP
        set limit-by-key enable
        set key-type http-header
        set key-name "Authorization"
        set key-pattern "Bearer (.*)"      # capture the token value
    next
end

✔ Caps spend and abuse per credential.   ✘ Only as granular as the keys you issue — give each app/team its own.

Worked example: rate-limiting Claude Code — match the right header

A coding agent like Claude Code makes direct calls to the model API, so it carries a credential on every request to /v1/messages — a natural per-credential rate-limit target. But the header depends on how it authenticates, and this is where most rules go wrong:

  • API-key auth (ANTHROPIC_API_KEY=sk-ant-api03-…) → the key travels in the x-api-key header. There is no Authorization header. The Anthropic API uses x-api-keyAnthropic API authentication — API keys are sent in the x-api-key header, not Authorization: Bearer. A rule that only matches Authorization will completely miss API-key traffic., not bearer auth.
  • OAuth / subscription login (claude /login or an OAuth proxy) → the token travels in Authorization: Bearer <token> (plus an anthropic-beta: oauth-2025-04-20 header). OAuth tokens are a different format (e.g. sk-ant-oat01-…), not sk-ant-api03-….

So match "Authorization: Bearer sk-ant-*" alone catches only the OAuth path. To cover both, scope the limit on whichever header is present:

fortiweb · per-credential limit, both auth modes (illustrative) 
config waf http-request-rate-limit
    edit claude-code-rate-limit
        set action block
        set limit-to-request 50
        set request-period 60
        set uri "/v1/messages"
        set limit-by-key enable
        # OAuth-auth Claude Code (subscription / proxy):
        set key-type http-header
        set key-name "Authorization"
        set key-pattern "Bearer (.*)"
    next
end

# API-key-auth Claude Code puts the secret here instead — add a
# second rule keyed on x-api-key so it isn't silently missed:
#   set key-name "x-api-key"

2

Enforce token format (regex)

Reject malformed or missing tokens up front. Anthropic keys begin with sk-ant-, OpenAI project keys with sk-proj- — FortiWeb can require that shape on the header before anything else runs:

fortiweb · token-format match (illustrative) 
set header-match "Authorization: Bearer sk-ant-*"   # require valid prefix
set action block                                    # else drop at the edge

✔ Cheaply rejects junk.   ✘ Confirms the token looks valid, not that it is valid.

3

Detect credential abuse & revoke fast

  • Rate-limit sources sending repeated requests with different or missing tokens — the signature of credential brute-forcingCredential brute-forcing — an attacker cycling through many candidate keys against an API to find one that works. A rapid stream of requests with varying or absent Authorization values is a strong behavioral tell, independent of whether any single token is valid..
  • Block leaked or revoked keys instantly with a Custom Rule that matches the token value — the moment a key shows up in a paste or alert, deny sk-ant-<leaked> at the edge without waiting on a backend redeploy.
  • Track failed-auth patterns over time to feed rate-limit and anomaly thresholds.

Token-handling hygiene

Never log full Bearer tokens — record only the last 4 characters or a hash, in FortiWeb logs and FortiAnalyzer alike. Rotate keys on a schedule, rate-limit aggressively on auth failures to blunt brute force, and when a key is confirmed compromised, revoke it through the provider's API and blocklist its shape on FortiWeb so the dead key never reaches them. FortiWeb screens the credential's value, shape, and behavior; the app still verifies its validity.

FortiWeb's real edge: ML-based anomaly detection

Here is the key point that rescues the WAF layer from the "no token semantics" limitation: you don't need to understand a prompt to recognize that traffic stopped looking normal. FortiWeb's ML-based anomaly detectionML-Based Anomaly Detection — a FortiWeb 8.0 feature that automatically learns the normal behavioral baseline of each protected URL and parameter (request rate, value length, character distribution, structure) and flags statistical deviations — no signatures, no hand-written rules. It is one of three FortiWeb ML engines, alongside ML-Based Bot Detection and ML-Based API Protection. learns a behavioral baseline for every API endpoint and parameter, then flags deviations from it — automatically, without signatures and without anyone writing a rule.[8]

An LLM DDoS, no matter how it is crafted, has to change the shape of your traffic to do damage. That shape change is exactly what the model is built to catch:

  • Volume deviation: a sudden request-rate spike against a learned baseline — the signature of a flood — registers as anomalous within minutes.
  • Parameter deviation: abnormally long prompt fields or oversized payloads diverge from the learned normal value length and distribution for that endpoint, surfacing token-flooding behavior structurally even though the WAF never tokenizes the text.
  • Behavioral deviation: unusual cadence, concurrency, or per-client patterns that don't match how real users have historically called the API.

Why the two-layer model matters here

FortiWeb's ML uses a two-layer design: the first layer builds the behavioral baseline and flags anomalies; the second layer validates whether a flagged anomaly is a genuine threat before acting. That second pass is what keeps the false-positive rate low — critical when the "block" decision could otherwise turn away paying customers during a traffic surge. Behavioral detection that you can't trust gets switched off; a two-layer model is what makes it safe to leave in block mode.[8]

Best practices & tuning

1. Baseline establishment (week 1–2)

  • Enable anomaly detection in "monitor" mode (log-only, no blocking).
  • Collect 7–14 days of traffic to establish baselines.
  • Review bot detection confidence scores to tune sensitivity.
  • Analyze legitimate user behavior to set appropriate rate limits.

2. Gradual enforcement (week 3–4)

  • Enable rate limiting for the top 10% of heavy users (those near the limit).
  • Switch anomaly detection to "block" mode with high thresholds.
  • Monitor for false positives; whitelist legitimate traffic as needed.
  • Adjust token limits based on user feedback.

3. Ongoing tuning

  • Review weekly metrics: false-positive rate, attack volume, cost savings.
  • Adjust bot detection sensitivity as attacker tactics evolve.
  • Update API schemas when the LLM API changes.
  • Collaborate with the security team to refine threat patterns.

4. Testing & validation

  • Run an internal DDoS simulation to verify FortiWeb blocking.
  • Test with legitimate heavy users to ensure no blocking.
  • Validate that metrics are accurate before sharing with stakeholders.
  • Document tuning decisions for future reference.

Why this matters

  • LLM DDoS is a cost attack, not just an availability attack — defenders must budget against blast radius, not just downtime.[3]
  • Generic HTTP rate limits key on source IP and miss the credential; token-aware (per-auth-token) rate limiting is now a baseline requirement.[1]
  • Bot fleets increasingly mimic legitimate users, so ML detection beats static rules and avoids the CAPTCHA tax on real customers.[2]
  • Multi-cloud LLM estates need consistent policy — single-cloud WAFs fragment enforcement.[2]
